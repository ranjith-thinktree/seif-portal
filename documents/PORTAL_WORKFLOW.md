# SEIF Portal — How the Portal Works (Workflow & Implementation Map)

Purpose

- This document explains how the SEIF Portal will behave at runtime: actors, core flows, how UI screens map to database tables and API endpoints, expected queries, and where to change behaviour in code/config. Use this as a reference when you ask for updates or when you make code changes.

Audience

- Product owners, frontend and backend developers, QA, and DevOps.

Summary of actors (roles)

- Partner: uploads center data (one CSV per center containing center, batch, and student details), manages profile, raises requests (refurbishment, data-correction), views notification inbox. Each partner manages multiple centers.
- Admin: reviews partner uploads, approves/rejects entire uploads with rejection reasons and remarks, manages partners and centers, processes refurbishment requests, can request partners to upload specific center data with scheduling options, and sends responses via the in-app notification system.
- SEIF_READONLY (SEIF HQ): read-only dashboards and export/reporting access.
- SUPER_ADMIN: full privileges for system setup and user management.

Core tables referenced
(See `db.sql` for the full schema.) Key tables used in flows below:

- `users`, `partners`, `centers`, `center_courses`, `batches`
- `data_uploads`, `uploaded_centers`, `uploaded_batches`, `uploaded_students` (staging area for partner uploads)
- `requests`, `scheduled_requests` (for admin-scheduled upload requests), `refurbishment_requests`, `refurbishment_packages`, `refurbishment_request_packages`
- `request_attachments`, `request_comments`
- `notifications` (in-app notifications)
- `download_logs`, `audit_logs`

High-level system components

- Frontend: React + Tailwind. UI screens call REST endpoints and show in-app notifications.
- Backend: Node.js + Express. Exposes REST API, connects to MySQL, reads/writes to S3 for files, and uses Redis + Bull for background workers.
- Database: MySQL with tables per `db.sql` (migrations required to convert Postgres dialect to MySQL).
- Real-time notifications: implemented via WebSocket (recommended) or Server-Sent Events (SSE). Messages are also stored in `notifications` table as source-of-truth.

Important design constraints

- Notifications: in-app only (no emails). The `notifications` table keeps read/unread state. Real-time channel sends new notifications to connected browser sessions.
- Uploads are staged: partner uploads go into `data_uploads` and `uploaded_centers` / `uploaded_batches` / `uploaded_students` for review. Admin approves/rejects the ENTIRE upload (not individual rows). Approved items are copied/linked into `centers`, `batches`, and a future `students` table.
- Upload approval granularity: admin reviews the complete upload and either approves everything or rejects everything with a detailed reason and remarks.
- Record identity: many tables use UUID primary keys. For MySQL migrations, UUIDs can be generated by the app and stored as CHAR(36) or BINARY(16).

Primary user flows (detailed)

1. Partner Login & Session

- UI: `Partner Login` screen (email/password; 'Forgot password' links to password reset flow).
- API endpoints:
  - POST /auth/login - body { email, password } -> returns JWT access token + refresh token
  - POST /auth/refresh - { refreshToken }
  - POST /auth/password-reset/request - { email }
  - POST /auth/password-reset/confirm - { token, newPassword }
- DB interactions:
  - Verify user credentials against `users.password_hash`.
  - On login success, update `users.last_login_at` and write an `audit_logs` entry.

2. Partner — Upload Data (center data with batches and students)

- UI: `Upload Data` screen with a form asking for: center name, batch number, batch start date, batch completion date, total students, male students, female students, and ONE CSV file containing all center, batch, and student details.
- Frontend behavior:
  - Partner fills the form and attaches ONE CSV file per center.
  - Validate file type (CSV), size client-side.
  - Upload CSV to S3 (signed URL) or send to backend endpoint for processing.
  - Create a `data_uploads` record with `status='pending'`, `file_url`, `uploaded_by`.
- API endpoints:
  - POST /uploads/init - init upload metadata, returns signed URL or upload token.
  - POST /uploads/complete - notify backend of uploaded file and create `data_uploads` row with form metadata.
- Backend behavior:
  - Store upload metadata in `data_uploads`.
  - Trigger background job to parse CSV and create rows in `uploaded_centers`, `uploaded_batches`, and `uploaded_students` tables (one row per student in CSV), all with `approval_status='pending'`.
  - Create an in-app notification using `notifications` for Admin role (recipient_role='ADMIN') that new upload is pending review.
- DB interactions:
  - INSERT into `data_uploads`.
  - INSERT into `uploaded_centers` (one row for the center).
  - INSERT into `uploaded_batches` (one row for the batch).
  - INSERT many into `uploaded_students` (one row per student from CSV).
  - Write `audit_logs` entries for the upload.

3. Admin — Review Uploads & Approve/Reject (entire upload)

- UI: `Admin Inbox` / `Data Review` screens showing paginated `data_uploads`. Admin opens an upload and sees all related `uploaded_centers`, `uploaded_batches`, and `uploaded_students` rows. Admin reviews the complete upload and decides to Approve or Reject everything at once.
- API endpoints:
  - GET /admin/uploads - list `data_uploads` (filter by status, partner_id)
  - GET /admin/uploads/:uploadId/details - get full details (uploaded_centers, uploaded_batches, uploaded_students for this upload)
  - POST /admin/uploads/:uploadId/approve - approve the entire upload
  - POST /admin/uploads/:uploadId/reject - body { rejection_reason, remarks } - reject the entire upload with detailed explanation
- Backend behavior on approve:
  - Create a transaction:
    - INSERT into `centers` from `uploaded_centers`, set `approval_status='approved'` and `approved_center_id`.
    - INSERT into `batches` from `uploaded_batches`, set `approval_status='approved'` and `approved_batch_id`.
    - INSERT into future `students` table from `uploaded_students`, set `approval_status='approved'` and `approved_student_id`.
    - UPDATE `data_uploads` status to 'approved'.
  - Add `audit_logs` entry and a `notifications` entry to the partner (recipient_id = partner user who uploaded) with approval message.
  - Send notification via real-time channel if partner is connected.
- Backend behavior on reject:
  - UPDATE `data_uploads` set `status='rejected'`, `rejection_reason`, `remarks`, `reviewed_by`, `reviewed_at`.
  - UPDATE all related `uploaded_centers`, `uploaded_batches`, `uploaded_students` set `approval_status='rejected'`, `rejection_reason`, `remarks`.
  - Add `audit_logs` entry and a `notifications` entry to the partner with rejection details (reason + remarks).
  - Send notification via real-time channel.
- DB interactions:
  - Transactional INSERT into `centers`, `batches`, future `students` table and UPDATE all uploaded\_\* rows on approval.
  - UPDATE `data_uploads` and all uploaded\_\* rows on rejection.

4. Requests & Refurbishment Flow (Partner → Admin → Approved)

- UI: Partner `Refurbishment Request` form: choose `refurbishment_packages`, select center(s), provide justification, upload photos (to S3), submit.
- API endpoints:
  - POST /requests - create request (type=refurbishment)
  - POST /requests/:id/attachments - upload supporting images (creates `request_attachments`)
  - POST /requests/:id/comments - add a comment (internal flag optional)
  - POST /requests/:id/assign - admin assigns request to admin user
  - POST /requests/:id/approve - admin approves
  - POST /requests/:id/reject - admin rejects
- Backend behavior:
  - Insert into `requests`. For refurbishments, insert into `refurbishment_requests` and related `refurbishment_request_packages`.
  - Admin can change `status` field on `requests` and add `reviewed_by` and `reviewed_at`.
  - Notifications are created for partner and admin participants for status changes.
- DB interactions:
  - INSERT into `requests`, `refurbishment_requests`, `refurbishment_request_packages`.
  - INSERT into `request_attachments` for uploaded files.
  - INSERT `request_comments` as needed.

5. Admin — Request Partner to Upload Data (scheduled requests)

- UI: Admin `Request Upload` form with fields: select partner, select center (optional), reason for request, description, attach file (optional), and scheduling options (immediate, monthly, quarterly, semi-annual, annual, or custom date range from-to).
- API endpoints:
  - POST /admin/requests/upload - create upload request with scheduling
  - GET /admin/requests/scheduled - list all scheduled requests
  - PUT /admin/requests/scheduled/:id - update or deactivate a scheduled request
- Backend behavior:
  - INSERT into `requests` with `type='upload_request'`, `partner_id`, `center_id` (optional), `title`, `description`, `status='pending'`, `created_by` (admin user ID).
  - INSERT into `scheduled_requests` with `request_id`, `recurrence_type` (immediate/monthly/quarterly/semi_annual/annual/custom), `start_date`, `end_date`, `next_scheduled_date`, `is_active=true`.
  - If recurrence_type is 'immediate', create a notification immediately. Otherwise, a background scheduler (cron job or worker) checks `scheduled_requests` daily and sends notifications when `next_scheduled_date <= today`, then updates `next_scheduled_date` based on recurrence.
  - Create `notifications` entry to partner (recipient_id or role) with the upload request details.
  - Attach file to `request_attachments` if provided.
- DB interactions:
  - INSERT into `requests`, `scheduled_requests`, `request_attachments` (if file attached).
  - Background scheduler queries `scheduled_requests WHERE is_active=true AND next_scheduled_date <= CURRENT_DATE` and creates notifications, then updates `next_scheduled_date` and `last_executed_at`.

6. Notifications (in-app only)

- Storage: `notifications` table is source-of-truth. Each notification row may be targeted at `recipient_id` or to `recipient_role` for broadcasts.
- Delivery:
  - When an event occurs (new upload, approval, rejection, request status change), create a `notifications` row with `sent_via='in_app'` and `is_read=false`.
  - If the recipient has an active WebSocket session, push the event over the socket.
  - UI reads notifications through GET /notifications and marks read via POST /notifications/:id/mark-read.
- Example endpoints:
  - GET /notifications?recipient_id=...&limit=25
  - POST /notifications/:id/mark-read
- Where to change behaviour:
  - Notification contents and logic live in backend event handlers (upload parser, admin approve endpoints, request status change handlers). To change wording or triggers, update those handlers.
  - Real-time transport: to switch from WebSocket to SSE, update the realtime module and client SDK.

7. Refurbishment Flow (Complete Course-Based Package Selection)

This flow allows admin to create refurbishment requests for eligible centers based on frequency, partner to select packages course-by-course with optional upgradation, and admin to review and approve/reject with detailed reasons.

**7.1 Admin Refurbishment Page (3 Tabs)**

- **UI:** Admin Refurbishment Dashboard with 3 main tabs:

  1. **Overview Tab** - Contains 3 sub-tabs:
     - **Eligible Centers:** Shows centers where `(CURRENT_DATE - last_refurbishment_date) >= refurbishment_frequency_months` OR `(CURRENT_DATE - year_of_establishment) >= refurbishment_frequency_months` for new centers. Includes center name, partner, last refurbishment date, frequency, courses offered.
     - **Last Refurbished:** Shows all centers sorted by most recently refurbished.
     - **All Centers:** Shows all centers with refurbishment status, last date, frequency.
  2. **Requests Tab** - Shows active refurbishment requests with `status IN ('pending', 'partner_submitted', 'in_review')`. Admin can click "Create Refurbishment Request" button. Displays request ID, center, partner, status, created date, assigned to.
  3. **Past Requests Tab** - Shows completed requests with `status IN ('approved', 'rejected', 'completed')`. Displays request ID, center, partner, status, reviewed date, admin remarks.

- **API Endpoints:**

  - `GET /admin/refurbishment/eligible-centers` - Query centers with eligibility calculation:
    ```sql
    SELECT c.id, c.center_name, c.partner_id, c.last_refurbishment_date,
           c.refurbishment_frequency_months, c.year_of_establishment,
           TIMESTAMPDIFF(MONTH, COALESCE(c.last_refurbishment_date, c.year_of_establishment), CURDATE()) as months_since_last
    FROM centers c
    WHERE TIMESTAMPDIFF(MONTH, COALESCE(c.last_refurbishment_date, c.year_of_establishment), CURDATE()) >= c.refurbishment_frequency_months
    ORDER BY months_since_last DESC
    ```
  - `GET /admin/refurbishment/requests?status=active` - List active requests
  - `GET /admin/refurbishment/requests?status=past` - List past requests
  - `GET /admin/refurbishment/last-refurbished` - List centers ordered by last_refurbishment_date DESC
  - `GET /admin/refurbishment/all-centers` - All centers with refurbishment details

- **Background Job:** Daily cron job checks eligibility and creates notifications for admin when centers become eligible. Updates `notifications` with `alert_type='refurbishment'`.

**7.2 Admin Creates Refurbishment Request**

- **UI:** Admin clicks "Create Refurbishment Request" → Modal/form with:

  - Select Center (dropdown filtered to eligible centers)
  - Select Courses (multi-select from center's courses via `center_courses` table)
  - For each course, admin pre-selects packages from `course_packages` WHERE course_id = selected_course
  - Add remarks/instructions for partner
  - Submit

- **API Endpoint:**
  - `POST /admin/refurbishment/create-request` - body { center_id, course_ids[], selected_packages_per_course{ course_id: [package_ids] }, remarks }
- **Backend Behavior:**

  1. INSERT into `refurbishment_requests` with `request_id` (FK to `requests`), `center_id`, `is_upgradation_requested=false`
  2. For each course, INSERT into `refurbishment_admin_selected_packages` with `refurbishment_request_id`, `course_id`, `package_id` (one row per package admin pre-selected)
  3. INSERT into `requests` with `type='refurbishment'`, `partner_id` (from center), `center_id`, `status='pending'`
  4. INSERT into `notifications` with `recipient_id` (partner user), `alert_type='refurbishment'`, `type='alert'`, `title='Refurbishment Request Created'`, `message`, `remark` (admin remarks), `related_entity_type='request'`, `related_entity_id=request_id`
  5. Send real-time notification to partner

- **DB Interactions:**
  - INSERT into `requests`, `refurbishment_requests`, `refurbishment_admin_selected_packages` (many rows)
  - INSERT into `notifications`

**7.3 Partner Inbox - Alerts Tab**

- **UI:** Partner Inbox with "Alerts" tab showing table columns:

  - Date (created_at)
  - Type (alert_type: 'refurbishment', 'data_approval', 'data_reject', 'upload_request')
  - Title (notification title)
  - Remark (admin's remark field)
  - Status (request status from related_entity_id)
  - Action (View button)

- **API Endpoint:**

  - `GET /partner/inbox/alerts` - Query:
    ```sql
    SELECT n.id, n.created_at, n.alert_type, n.title, n.remark,
           r.status, n.related_entity_id
    FROM notifications n
    LEFT JOIN requests r ON r.id = n.related_entity_id AND n.related_entity_type = 'request'
    WHERE n.recipient_id = ? AND n.type = 'alert'
    ORDER BY n.created_at DESC
    ```

- **Partner clicks "View"** → Opens refurbishment request details page

**7.4 Partner Refurbishment Request - Center Details & Course-by-Course Selection**

- **UI:** Partner views refurbishment request with:

  1. **Header:** Center name, address, courses offered, admin remarks
  2. **Course Tabs:** One tab per course (e.g., "Electrical", "Solar", "Industrial Automation")
  3. **Per Course Tab:**
     - Shows only packages admin pre-selected for this course (from `refurbishment_admin_selected_packages`)
     - Checkboxes for partner to select needed packages
     - Text area for "Justification" (why these packages are needed)
     - Image upload area for "Current Condition Photos" (multiple images)
  4. **Upgradation Section (Optional):**
     - Checkbox "Request Room Upgradation"
     - If checked, form appears: Room dimensions (length, breadth, height in feet), justification text, image upload for room photos
  5. **Preview Screen:** Shows all courses in tabs with partner selections, justifications, and photos for final review
  6. **Submit Button**

- **API Endpoints:**

  - `GET /partner/refurbishment/:requestId/details` - Returns center details, courses, admin-selected packages per course:

    ```sql
    SELECT rr.*, c.center_name, c.address, r.remarks as admin_remarks,
           cc.course_id, co.course_name,
           rasp.package_id, rp.package_name, rp.description
    FROM refurbishment_requests rr
    JOIN requests r ON r.id = rr.request_id
    JOIN centers c ON c.id = rr.center_id
    JOIN center_courses cc ON cc.center_id = c.id
    JOIN courses co ON co.id = cc.course_id
    JOIN refurbishment_admin_selected_packages rasp ON rasp.refurbishment_request_id = rr.id AND rasp.course_id = cc.course_id
    JOIN refurbishment_packages rp ON rp.id = rasp.package_id
    WHERE rr.request_id = ?
    ORDER BY co.course_name, rp.package_name
    ```

  - `POST /partner/refurbishment/:requestId/submit` - body { courses: [{ course_id, package_ids[], justification, attachments[] }], upgradation: { length, breadth, height, justification, photos[] } }

- **Backend Behavior on Submit:**

  1. UPDATE `requests` set `status='partner_submitted'`
  2. For each course:
     - For each selected package, INSERT into `refurbishment_request_course_packages` with `refurbishment_request_id`, `course_id`, `package_id`, `partner_justification`
     - For each photo, upload to S3 and INSERT into `refurbishment_request_course_attachments` with `refurbishment_request_id`, `course_id`, `file_url`, `file_name`, `uploaded_by`
  3. If upgradation requested:
     - UPDATE `refurbishment_requests` set `is_upgradation_requested=true`
     - INSERT into `refurbishment_upgradation_rooms` with `refurbishment_request_id`, `length`, `breadth`, `height`, `justification`
     - For each upgradation photo, upload to S3 and INSERT into `refurbishment_upgradation_photos` with `refurbishment_request_id`, `file_url`, `file_name`
  4. INSERT into `notifications` for admin with `alert_type='refurbishment'`, `title='Partner Submitted Refurbishment Request'`, `related_entity_id=request_id`
  5. Send real-time notification to admin

- **DB Interactions:**
  - UPDATE `requests.status`
  - INSERT many into `refurbishment_request_course_packages` (one per selected package per course)
  - INSERT many into `refurbishment_request_course_attachments` (one per photo per course)
  - INSERT into `refurbishment_upgradation_rooms` (if upgradation requested)
  - INSERT many into `refurbishment_upgradation_photos` (if upgradation requested)
  - INSERT into `notifications`

**7.5 Admin Reviews Refurbishment Request**

- **UI:** Admin sees refurbishment request in "Requests" tab with `status='partner_submitted'`. Admin clicks "Review" → Status changes to `in_review`. Review page shows:

  1. **Header:** Center details, partner name, submission date
  2. **Course Tabs:** Same structure as partner view, showing:
     - Course name
     - Table of selected packages with partner justification
     - Gallery of photos partner uploaded for this course
  3. **Upgradation Section:** If requested, shows room dimensions, justification, photos
  4. **Admin Actions:**
     - Approve button → Modal for admin remarks
     - Reject button → Modal for rejection reason and remarks
  5. **Comments Section:** Admin can add internal comments visible to other admins

- **API Endpoints:**

  - `GET /admin/refurbishment/:requestId/review` - Returns full submission with course packages, attachments, upgradation details:

    ```sql
    SELECT rr.*, c.center_name, p.organization_name,
           rrcp.course_id, co.course_name, rrcp.package_id, rp.package_name, rrcp.partner_justification,
           rrca.file_url as course_photo_url,
           rur.length, rur.breadth, rur.height, rur.justification as upgradation_justification,
           rup.file_url as upgradation_photo_url
    FROM refurbishment_requests rr
    JOIN requests r ON r.id = rr.request_id
    JOIN centers c ON c.id = rr.center_id
    JOIN partners p ON p.id = c.partner_id
    LEFT JOIN refurbishment_request_course_packages rrcp ON rrcp.refurbishment_request_id = rr.id
    LEFT JOIN courses co ON co.id = rrcp.course_id
    LEFT JOIN refurbishment_packages rp ON rp.id = rrcp.package_id
    LEFT JOIN refurbishment_request_course_attachments rrca ON rrca.refurbishment_request_id = rr.id AND rrca.course_id = rrcp.course_id
    LEFT JOIN refurbishment_upgradation_rooms rur ON rur.refurbishment_request_id = rr.id
    LEFT JOIN refurbishment_upgradation_photos rup ON rup.refurbishment_request_id = rr.id
    WHERE rr.request_id = ?
    ORDER BY co.course_name, rp.package_name
    ```

  - `POST /admin/refurbishment/:requestId/review` - Change status to `in_review` (admin clicked review button)

  - `POST /admin/refurbishment/:requestId/approve` - body { admin_remarks }

  - `POST /admin/refurbishment/:requestId/reject` - body { rejection_reason, admin_remarks }

- **Backend Behavior on Approve:**

  1. UPDATE `requests` set `status='approved'`, `reviewed_by` (admin user ID), `reviewed_at=NOW()`
  2. UPDATE `centers` set `last_refurbishment_date=CURDATE()` for the center
  3. INSERT into `notifications` for partner with `alert_type='refurbishment'`, `title='Refurbishment Approved'`, `message`, `remark` (admin remarks)
  4. INSERT into `audit_logs` with action='refurbishment_approved'
  5. Send real-time notification to partner

- **Backend Behavior on Reject:**

  1. UPDATE `requests` set `status='rejected'`, `rejection_reason`, `remarks` (admin remarks), `reviewed_by`, `reviewed_at=NOW()`
  2. INSERT into `notifications` for partner with `alert_type='refurbishment'`, `title='Refurbishment Rejected'`, `message`, `remark` (rejection reason + remarks)
  3. INSERT into `audit_logs` with action='refurbishment_rejected'
  4. Send real-time notification to partner

- **DB Interactions:**
  - UPDATE `requests.status`, `requests.reviewed_by`, `requests.reviewed_at`
  - UPDATE `centers.last_refurbishment_date` (on approval)
  - INSERT into `notifications`, `audit_logs`

**7.6 Status Flow Summary**

Refurbishment request status progression:

- **pending:** Admin created request, waiting for partner to view and submit
- **partner_submitted:** Partner submitted course selections and optional upgradation
- **in_review:** Admin clicked "Review" button, actively reviewing submission
- **approved:** Admin approved with remarks
- **rejected:** Admin rejected with reason and remarks
- **completed:** (Future) After physical refurbishment completion, admin marks as completed

**7.7 Where to Change Behavior**

- **Eligibility calculation:** Change frequency logic in `GET /admin/refurbishment/eligible-centers` query. Currently uses `refurbishment_frequency_months` field in `centers` table. Background job runs daily to check and create notifications.
- **Package selection restrictions:** Partner can only select from admin pre-selected packages stored in `refurbishment_admin_selected_packages`. To allow partner to request additional packages, add a "Request Additional Package" feature with justification.
- **Upgradation flow:** Currently one room per request (schema supports multiple for future). To allow multiple rooms, modify UI and backend to accept array of rooms in submit endpoint.
- **Course filtering:** Courses displayed to partner are fetched from `center_courses` table. To change which courses are eligible for refurbishment, update `center_courses` relationships.
- **Notification triggers:** Change notification creation in create-request, submit, approve, and reject endpoints to modify alert content, recipients, or timing.

8. SEIF Read-only Dashboards & Reports

- UI: aggregated stats, map visualization, partner insights, filters, export button.
- API endpoints:
  - GET /reports/partners?filters...
  - GET /reports/centers?filters...
  - POST /reports/export - creates `download_logs` entry and returns a pre-signed file URL.
- DB interactions:
  - Reports will perform aggregated queries (COUNT, SUM, GROUP BY) on `centers`, `batches`, `data_uploads`, and `requests` and may reference `download_logs`.

Mapping screens to DB + endpoints (quick table)

- Partner Login -> `users` -> /auth/login
- Partner Dashboard overview -> aggregated queries on `data_uploads` (partner_id), `requests` (partner_id), `notifications` (recipient_id/role)
- Upload Data -> `data_uploads` (insert) -> background worker -> `uploaded_centers` / `uploaded_batches` / `uploaded_students`
- Data Management -> `centers` / `batches` -> GET /centers, GET /batches
- Inbox -> `notifications` -> GET /notifications (filtered), POST /notifications/:id/mark-read
- Admin Partner List -> `partners` -> GET /admin/partners
- Admin Review Uploads -> `data_uploads`, `uploaded_centers`, `uploaded_batches`, `uploaded_students` -> GET endpoints; approve entire upload -> create `centers`/`batches`/future `students` rows
- Admin Request Upload -> POST /admin/requests/upload -> `requests` + `scheduled_requests` tables
- Refurbishment form -> POST /requests + `refurbishment_requests` and `refurbishment_request_packages` tables

Where to change behavior (developer guide)

- Upload parsing rules and mapping: look at the background worker / parser module. Changing validation, CSV column mapping, or auto-corrections is done here (and will affect what gets inserted into `uploaded_centers`, `uploaded_batches`, and `uploaded_students`).
- Approval granularity: Currently admin approves/rejects the ENTIRE upload. If you want to allow per-row approval in the future, modify the approval endpoint to accept row IDs and loop through approvals, or add a bulk approval API.
- Approval rules: Admin approve endpoint. If you want to auto-approve some records based on simple heuristics, add that logic to the approval endpoint or to the background job that flags uploads for auto-approval.
- Scheduled request recurrence: The background scheduler (cron job or Bull worker) runs daily and checks `scheduled_requests` table for due requests. Modify the scheduler frequency or logic in the worker file.
- Notifications text & triggers: change event handler code that creates rows in `notifications`.
- Read-only vs write permissions: RBAC enforced in middleware (auth middleware and route guards). Update permission checks there to change what each role can access.
- File storage: S3 bucket config in environment variables (UPLOAD_BUCKET, UPLOAD_REGION); changing bucket or expiration policy affects how files are uploaded and downloaded.
- UUID handling / PK type: if you want different key strategies (auto-increment vs UUID), change table creation migrations and model definitions.

Common SQL snippets (examples)

- List pending uploads for an admin:

```
SELECT du.*
FROM data_uploads du
WHERE du.status = 'pending'
ORDER BY du.created_at DESC
LIMIT 50;
```

- Get full upload details (center, batches, students):

```
SELECT uc.*, ub.*, us.*
FROM data_uploads du
LEFT JOIN uploaded_centers uc ON uc.data_upload_id = du.id
LEFT JOIN uploaded_batches ub ON ub.data_upload_id = du.id
LEFT JOIN uploaded_students us ON us.data_upload_id = du.id
WHERE du.id = ?
```

- Approve entire upload (conceptual transaction):

  1. INSERT INTO centers SELECT ... FROM uploaded_centers WHERE data_upload_id = ?
  2. UPDATE uploaded_centers SET approval_status='approved', approved_center_id = LAST_INSERT_ID() WHERE data_upload_id = ?
  3. INSERT INTO batches SELECT ... FROM uploaded_batches WHERE data_upload_id = ?
  4. UPDATE uploaded_batches SET approval_status='approved', approved_batch_id = LAST_INSERT_ID() WHERE data_upload_id = ?
  5. INSERT INTO students SELECT ... FROM uploaded_students WHERE data_upload_id = ? (future table)
